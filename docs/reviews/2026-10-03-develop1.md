## Summary

Secured sessions adds eligibility gating for two modes (allowlist and approval), an admin participant roster, and a `VoteParticipation` audit trail, with an unusually honest `verify.md` and a strong new regression suite. The gating itself is only implemented on the REST join endpoint. Three other doors into the same session (the legacy `join_session` socket event, the `subscribe_session` room join, and the public `GET /api/sessions` listing) were left open, so an outsider can still list secured sessions, read their live state, and join and vote in one. A fourth path fails open when `whoCanJoin` is not a recognised value.

## Blockers

### 🔴 `join_session` socket event skips the eligibility gate entirely, `voting-server/src/server.js:1717`
**Problem**: The allowlist and approval checks (AC-4, AC-5) live only inside `POST /api/sessions/:sessionId/join` (the `if (isSecured)` block at `server.js:1065`). The socket `join_session` handler at `server.js:1717` reads `sessionId`, `displayName` and the handshake derived `socket.data.userId`, then calls `registerVoter` directly at `server.js:1723`. `registerVoter` (`voting-server/src/auth/voter.js:36`) checks only that the session exists and is not archived. There is no `SessionAllowlistEntry` or `SessionJoinRequest` lookup anywhere on this path, and no eligibility check at `VOTE` time either.
**Why it matters**: Any socket.io client that knows a session id can emit `join_session` with `{ sessionId, displayName }`, receive a valid `voterToken`, subscribe, and cast a vote in a secured session. The session id is free: `GET /api/sessions` lists it, and `GET /api/join/:code` returns it by design (AC-9). The shipped React client no longer calls `join_session` (zero references under `voting-client/src`), so the UI is safe, but the endpoint is live and unauthenticated. The entire eligibility feature rests on one door being closed.
**Suggested fix**: Extract the secured eligibility check from the REST handler into one shared helper (cookie or socket handshake identity in, allowlist/approval decision out) and call it from `join_session` before `registerVoter`, returning an error through the ack callback. Add a regression test that an anonymous socket joining a secured session over `join_session` is refused.

**Resolution (2026-10-03): Fixed.** `resolveSessionAccess` and `evaluateSecuredEligibility` in `voting-server/src/server.js` are now the single gate, called from both `POST /api/sessions/:sessionId/join` and the `join_session` event before `registerVoter`. Section 5 of `voting-server/test/secured_sessions_regression_spec.js` covers five cases: anonymous refused, signed in outsider refused, allowlisted voter admitted, approval flow returning pending before admitting once approved, and public anonymous join unchanged. Server suite: 623 passing.

### 🟠 `GET /api/sessions` still lists secured sessions with their join codes, `voting-server/src/server.js:1288`
**Problem**: `broadcastSessions` and `getSocketSessionsSummary` (`server.js:430-460`) filter `type !== 'secured'` for non admin sockets, but the REST discovery route at `server.js:1288` returns `getSessionsSummary(actualStore.getState())` unfiltered, to any anonymous caller.
**Why it matters**: AGENTS.md states that secured sessions are hidden from voter facing broadcasts, and hiding the listing is what makes the socket filtering meaningful. As written, anyone can enumerate every secured session's id, title, status, `whoCanJoin` and `joinCode` without authenticating, which is the input the two findings above need. The socket side of the same policy is enforced and tested; the REST side is not.
**Suggested fix**: Apply the same filter to this response (and any other voter facing session list), returning only `type !== 'secured'` sessions to unauthenticated callers. Add a regression test asserting a secured session id never appears in the anonymous REST payload.

**Resolution (2026-10-03): Fixed.** A new `filterSessionsForCaller(summaries, isAdmin)` is now shared by the socket summary, the broadcast, and this REST route. An anonymous caller gets the filtered list; a caller presenting `Authorization: Bearer <admin JWT>` (the pattern `GET /api/auth/me` already uses) gets the full one. Test 7 in `secured_sessions_regression_spec.js` covers both.

### 🟠 `subscribe_session` joins the room with no eligibility check, `voting-server/src/server.js:1815`
**Problem**: `subscribe_session` validates that the session exists and then does `socket.join(roomName)` at `server.js:1815` before it looks at any voter token. Token validation afterwards only decides whether presence is recorded. Membership in `session:<id>` is what gates `session_state`, `lobby_update` and `presence_update`.
**Why it matters**: An outsider with a session id (see above) receives the authoritative state of a secured session: title, candidates, round history and the frozen tally at `RESULTS_REVEALED` or completion (`applyTallyVisibilityGuard` hides tallies only during an active round, `server.js:226`). Securing the roster while leaving the results room open gives the feature a privacy hole on the exact sessions it is meant to protect.
**Suggested fix**: For sessions with `type === 'secured'`, require a valid voter token (or admin) before joining the room, and reject otherwise, the way `subscribe_participants` already rejects non admins. Cover it with a test that an anonymous socket subscribing to a secured session receives no `session_state`.

**Resolution (2026-10-03): Fixed.** The handler now resolves identity before touching the room: on a secured session it admits `isSocketAdmin(socket)` or a token that passes `validateVoterToken`, and otherwise emits `action_error` with `NOT_ELIGIBLE` and returns without joining. The check reads `type` from the store synchronously, because an `await` here delayed the room join past a broadcast the client triggers right after subscribing (caught by `ingress_allowlist_spec.js`). Test 6 covers outsider refused, allowlisted voter served, admin served, public session unchanged.

### 🟠 Fail open when a secured session's `whoCanJoin` is `public` or unknown, `voting-server/src/server.js:1065`
**Problem**: The gate is `if (whoCanJoin === 'allowlist') { ... } else if (whoCanJoin === 'approval') { ... }`. Any other value, including the literal `'public'`, falls straight through both branches and execution continues into `registerVoter`. Ingress validation rejects `'public'` at `CREATE_SESSION` now, but that validation did not exist before spec 0007, so any secured session persisted earlier (or written directly) carries `whoCanJoin: 'public'`, the schema default.
**Why it matters**: Security gates should fail closed. A single legacy row makes a secured session behave exactly like a public one, silently, with no log line.
**Suggested fix**: Invert the shape: for a secured session, deny unless `whoCanJoin` matches a known mode and the corresponding check passes, and log a warning when the mode is unusable. Add a test that a secured session with `whoCanJoin: 'public'` refuses join with 403.

**Resolution (2026-10-03): Fixed.** `evaluateSecuredEligibility` ends in a deny branch with a `console.error` for an unusable mode, so a secured session with `whoCanJoin: 'public'` can no longer fall through into `registerVoter`, on either entry point.

### 🟠 Secured sessions accept joins after `START_SESSION`, contrary to the locked roster invariant, `voting-server/src/server.js:1065`
**Problem**: The spec's key invariant reads "After `START_SESSION`, no new joins or approval changes are accepted. The eligibility roster is locked." The join path checks eligibility but never the session status (only `registerVoter`'s archived check runs). An allowlisted voter who never joined can join while the session is `open`; an approved voter who was absent at start can do the same.
**Why it matters**: `voterCount` feeds quorum and the round eligibility snapshot, so a late joiner changes the completion condition mid session. If the intent is to allow late approved voters, the spec invariant should say so; if not, the gate is missing a check the document promises.
**Suggested fix**: Decide which behaviour is correct, then enforce it at the join endpoint for secured sessions (reject `open` unless the spec is amended), and pin the chosen behaviour with a test.

**Resolution (2026-10-03): Fixed, spec side chosen.** `resolveSessionAccess` now also returns `status`, and `evaluateSecuredEligibility` refuses any secured join once the session is not `pending` with `409 SESSION_STARTED`, before the mode checks and before any request row can be created (so the approval queue also closes at Start, per AC-8). A voter who already holds a valid `user:<id>` token for the session may still rejoin, so clearing browser storage mid session does not lock out a participant, and removal still holds because the allowlist entry or request behind them is gone. Section 8 of the regression spec pins all five cases: REST refusal, socket refusal, approval queue closed with no row created, pre start voter rejoining, and a public session unaffected.

## Minor

### 🟡 Admin roster stops updating after any socket reconnect, `voting-client/src/pages/Admin.jsx:170`
`subscribe_participants` is emitted only when `managingSessionId` changes. Server side the subscription is room membership (`participants:<id>`), which disappears on disconnect. The new `applyAdminTokenToSocket` forces a reconnect on every admin login and logout, and Socket.io also auto reconnects on network blips, so the participant panel silently freezes: pending requests, counts, and approvals stop arriving until the admin closes and reopens Manage. `connectSocketToStore`'s `connect` handler re-emits `subscribe_session` for room subscriptions but knows nothing about the roster. Re-emit `subscribe_participants` from a `connect` listener while a session is being managed (or have the server re-join known admin rooms).

### 🟡 `test-preferences.json` does not know about the new Vitest suite, `test-preferences.json`
The file still says `"tool": "node:test"`, `"additionalTools": []`, `"filePattern": "*_spec.js"`. This change adds Vitest with `test/**/*.test.jsx` and rewrites the client `npm test` to run both runners. Any tooling that discovers tests from this file will miss `lobby_secured.test.jsx` entirely. Add Vitest to `additionalTools` (and the `.test.jsx` pattern) so the two runners are both visible.

## Strengths

- `docs/specs/0007-secured-sessions/verify.md` is unusually honest: it records how the run was launched, that the server never reads `.env`, and it documents the admin handshake defect it found and fixed rather than quietly closing the checklist.
- `voting-server/test/secured_sessions_regression_spec.js` targets the right regression risks: all five action names present in `ADMIN_ACTION_TYPES`, `VoteParticipation` having no vote choice field under any spelling, the roster refusing anonymous, forged and cookie-only sockets, and line numbered allowlist validation.
- The REST join gate itself fails closed when MongoDB is down (allowlist miss returns 403, approval falls back to a pending request rather than admitting the voter), and the identity is always derived from the verified `vs_voter` JWT, never a client claim.
- The admin handshake fix in `socket.js` / `auth.js` is correct about Socket.io semantics (`auth` is only sent at handshake time), keeps `ADMIN_TOKEN_KEY` re-exported so no importer breaks, and arrives with 20 focused unit tests including the "token present before module load" case.

# Review, develop1, 2026-09-21

**Reviewed by**: session model, inline (no subagent spawning in this client, so the cross model guarantee is degraded; the reviewer may share the author model's blind spots)
**Scope**: 163 files changed vs main (review depth focused on the core source: server engine, auth, db layer, timers, client store, socket, auth)
**Verdict**: Blocked at review time. Cleared on 2026-09-21: the blocker, all four majors, and all four minors are fixed, each with its root cause and fix noted inline below and a regression test added. The five nits remain open.

## Summary

The change is the full VoteSphere app: an authoritative Immutable.js Redux tournament server over Socket.io with Mongo persistence, timers, and round lifecycle, plus a normalized Redux Toolkit client. The core design is genuinely solid: round closure funnels through an idempotent gate, stale timer callbacks are guarded, tests are extensive on both sides, and the client sanitizes tokens out of Redux. The headline problem is one real authorization hole: the ingress fallthrough dispatches any unlisted action type straight into the authoritative store, and `SET_ROUND_LIFECYCLE` is not in the admin allowlist, so any unauthenticated socket client can rewrite round state and the frozen vote snapshot.

## Blockers

### 🔴 Unauthenticated clients can dispatch SET_ROUND_LIFECYCLE and forge round state, `voting-server/src/server.js:941` and `voting-server/src/reducer.js:100`

**Problem**: The socket action ingress only guards actions listed in `ADMIN_ACTION_TYPES` (`CREATE_SESSION`, `START_SESSION`, `ARCHIVE_SESSION`, `SET_ENTRIES`, `NEXT`) and token checks `VOTE`. Everything else falls into the section 3 branch, `actualStore.dispatch(action)`, with no check at all. `SET_ROUND_LIFECYCLE`, which `roundManager` dispatches internally, is not in the admin set, and the reducer accepts it for any existing session.

**Why it matters**: Any connected client, no token needed, can emit `{ type: 'SET_ROUND_LIFECYCLE', sessionId, lifecycle: 'VOTING', finalVote: { pair, tally } }`. That reopens a closed round (votes accepted after `ROUND_CLOSED`), plants an arbitrary `finalVote` snapshot that the results UI renders as authoritative revealed results, and clears or replaces `revealTimer`. It breaks the project rule that the server alone decides round state, and it silently corrupts results that users see. A hostile client can also freely dispatch other unlisted internal action types into the store.

**Suggested fix**: Use an allowlist at ingress. Either add `SET_ROUND_LIFECYCLE` to `ADMIN_ACTION_TYPES` (it is a privileged state mutation, even when the runtime itself dispatches it) or introduce a separate internal dispatch path, for example `store.dispatchInternal`, that bypasses the socket ingress, and reject every socket action type not explicitly permitted. Add a regression test that emits `SET_ROUND_LIFECYCLE` over an anonymous socket and asserts rejection.

**Resolution (2026-09-21): Fixed.**
**Root cause**: the socket `action` ingress guarded only the admin allowlist and the VOTE token check. Every action type outside `ADMIN_ACTION_TYPES` fell through to the final `actualStore.dispatch(action)` branch, so internal types such as `SET_ROUND_LIFECYCLE` and any invented type reached the authoritative store with no authentication.
**Fix**: a complete ingress allowlist. `ALLOWED_ACTION_TYPES` (the five admin types plus `VOTE`) is checked first in the `action` handler; anything else is answered with `action_error FORBIDDEN_ACTION` and never reaches auth or the store. Internal runtime dispatches never travel through socket ingress, so no client path to `SET_ROUND_LIFECYCLE` remains.
**Regression test**: `voting-server/test/ingress_allowlist_spec.js` (anonymous internal action rejected, allowed actions unaffected).

## Major

### 🟠 CORS reflects any origin together with credentials, `voting-server/src/server.js:111` and `voting-server/src/server.js:446`

**Problem**: `setCorsHeaders` echoes back `req.headers.origin` verbatim and sets `Access-Control-Allow-Credentials: true`. The Socket.io server is configured with `origin: '*'` and `credentials: true`.

**Why it matters**: Any website a user visits can make credentialed cross origin calls to this API and read the responses. The voter join response carries the voter token, so a malicious page can obtain tokens from a visitor who has used the app. SameSite Lax on the cookie limits some of it, but the reflected origin plus credentials combination defeats the browser's same origin protection for reads.

**Suggested fix**: Allow a fixed set of origins from configuration (the dev client origin plus production origins), and only reflect the origin when it is on that list. For Socket.io, list explicit origins instead of `*`.

**Resolution (2026-09-21): Fixed.**
**Root cause**: `setCorsHeaders` echoed the request origin verbatim while always setting `Access-Control-Allow-Credentials: true`, and the Socket.io server was configured with `origin: '*'` plus credentials. A reflected origin combined with credentials defeats the browser same origin check, so any page could read credentialed responses, including voter tokens.
**Fix**: an origin allowlist read from `CORS_ALLOWED_ORIGINS` (comma separated, defaulting to the local dev client origins, with a development only `*` wildcard). `isOriginAllowed` gates both the HTTP header path and the Socket.io cors callback, so unlisted origins get no credentialed headers. `.env.example` documents the knob and the helpers are exported for tests.
**Regression test**: `voting-server/test/review_majors_regression_spec.js`, CORS describe (allow, reject, default list, wildcard).

### 🟠 Admin NEXT during the reveal window double advances the tournament, `voting-server/src/roundManager.js:640` and `voting-server/src/timer.js:520`

**Problem**: If an admin dispatches `NEXT` while the session is in `RESULTS_REVEALED`, the reducer processes it: it has no reveal window guard, only checks archived, winner, and entries. The store subscriber then early returns in `onStateChange` because `activeRevealTimers` still holds the session, so the new round gets no `initRound` and no voting timer. When the reveal timer fires, `expireReveal` finds the old round object still active with `revealExpired` false and dispatches a second `NEXT`.

**Why it matters**: One reveal produces two round advances, and the round the admin thought it started never gets a timer, so it can hang open with no countdown. We confirmed the adjacent behavior works when nobody touches NEXT during the window, and the client admin panel exposes NEXT, so this is reachable in normal use.

**Suggested fix**: Guard `NEXT` in the reducer against the `RESULTS_REVEALED` lifecycle (the reveal timer owns advancement), or have the NEXT path clear the active reveal timer and mark `revealExpired` before advancing. Add a spec: start a round, close it into the reveal window, dispatch NEXT, let the reveal expire, assert exactly one advance.

**Resolution (2026-09-21): Fixed.**
**Root cause**: `NEXT` had no guard for the `RESULTS_REVEALED` window, and the store subscriber skips `initRound` while the session still holds an active reveal timer. An admin NEXT inside the window therefore advanced once into a round with no timer, and when the pending reveal timer fired, `expireReveal` found the old round still active with `revealExpired` false and dispatched a second advance.
**Fix**: `consumeRevealExpiry(sessionId, roundId)` in `roundManager.js` marks the pending reveal expiry as consumed, and the reducer's `NEXT` case calls it whenever it advances during `RESULTS_REVEALED`. The stale timer can no longer produce a second advance, and the new round gets its voting timer through the normal subscriber path.
**Regression test**: `voting-server/test/reveal_next_regression_spec.js` (NEXT inside the window, then reveal expiry, exactly one advance).

### 🟠 Duplicate vote key is pair based, not round based, `voting-server/src/auth/voter.js:155`

**Problem**: `buildVoteKey` is `${sessionId}:::${sortedPair}:::${token}`. The claim in the project docs says round identity is the monotonic `${sessionId}:::r${roundIndex}`, but the duplicate check never sees the roundId.

**Why it matters**: In a pairwise tournament with ties, the same two candidates can be paired again in a later round. When that happens, every voter who voted in the earlier meeting is wrongly rejected with `DUPLICATE_VOTE` in the later round, and with an odd voter count that can stall the round until its timer runs out. The server code (ingress passes `pairArray` to `canCastVote`) and the docs disagree about what the key means.

**Suggested fix**: Thread the current `roundId` into `canCastVote` and `buildVoteKey` and make the key `${sessionId}:::${roundId}:::${sortedPair}:::${token}`, or document explicitly that a pair may face at most once per tournament and enforce that invariant in `core.js`.

**Resolution (2026-09-21): Fixed.**
**Root cause**: `buildVoteKey` built `${sessionId}:::${sortedPair}:::${token}` with no round component, and the VOTE ingress passed only the pair. When a tie brought the same two candidates together again in a later round, the earlier meeting's key matched and every voter was wrongly rejected with `DUPLICATE_VOTE`, which with an odd voter count could stall the round until its timer ran out.
**Fix**: the VOTE ingress resolves the current round id through `roundManager.getCurrentRoundId` and threads it into `canCastVote` and `buildVoteKey`, so the key is now `${sessionId}:::${roundId}:::${sortedPair}:::${token}`. The legacy pair scoped shape remains as a fallback when no round id exists.
**Regression test**: `voting-server/test/review_majors_regression_spec.js` (vote in round 1, duplicate rejected, same pair accepted in round 2) plus the updated `auth_spec.js` cases.

### 🟠 Synchronous bcrypt on the event loop plus no rate limit on login, `voting-server/src/auth/admin.js:53` and `voting-server/src/server.js:163`

**Problem**: `seedAdmin` uses `bcrypt.hashSync` and `verifyAdminCredentials` uses `bcrypt.compareSync`, both called directly inside the HTTP request handler and the `admin_login` socket handler. There is no rate limiting or attempt throttling on either login path.

**Why it matters**: Each compare blocks the single threaded event loop for the full bcrypt cost, so a burst of login attempts freezes voting timers, socket broadcasts, and round closure for every connected user, and brute force attempts double as a denial of service. The single admin account with a known default password (`adminPassword123!` when env is missing) makes throttling the one thing standing between the internet and the admin panel.

**Suggested fix**: Switch to the async `bcrypt.compare` / `bcrypt.hash` variants, and add a small in-memory attempt limiter per address (for example, exponential backoff after five failures) on both the REST and socket login paths. Warn loudly at startup when credentials fall back to defaults.

**Resolution (2026-09-21): Fixed.**
**Root cause**: `seedAdmin` used `bcrypt.hashSync` and `verifyAdminCredentials` used `bcrypt.compareSync` directly inside the HTTP request handler and the socket `admin_login` handler, so every attempt blocked the single threaded event loop for the full bcrypt cost, and neither login path had any limiter, which let brute force double as denial of service.
**Fix**: `verifyAdminCredentials` is now async on `bcrypt.compare` and both call sites await it, so the event loop stays free. A limiter counts consecutive failures and answers with `TOO_MANY_ATTEMPTS` (HTTP 429 on the REST path) after five failures, with exponential backoff from 1 second to 60 and a reset on success. REST `/api/admin/login` and socket `admin_login` share it. **Hardened the same day**: the limiter originally keyed on the presented identifier, which an attacker could rotate; it now keys on the client IP (`resolveClientIp` in `server.js`, socket address unless `TRUST_PROXY=true`, then `x-forwarded-for`) with one shared pool for unknown identifiers, so rotating identifiers from one address or rotating addresses against unknown identifiers both trip the limit, and the shared pool can never lock out the real admin identifier. See `test/ip_throttle_regression_spec.js`.
**Regression test**: `voting-server/test/review_majors_regression_spec.js` throttle describe; `test/auth_spec.js` updated for the async signature with a throttle reset between suites.

## Minor

### 🟡 Voter registries grow without bound, `voting-server/src/auth/voter.js`

**Problem**: `votersByToken`, `recordedVotes`, and `tokensBySession` only ever grow. Nothing removes a session's tokens or vote keys when the session completes or is archived.

**Why it matters**: On a long running public server, memory use climbs with every join and every vote, forever. It is a slow leak rather than a crash, but it caps the practical lifetime of a deployment.

**Suggested fix**: On `ARCHIVE_SESSION` and on session completion, drop the session's tokens and recorded vote keys (you already index tokens per session, so the cleanup is cheap).

**Resolution (2026-09-21): Fixed.** `releaseSessionVoters(sessionId)` drops the session's tokens, headcount index, and recorded vote keys (legacy key shape included). The store subscriber calls it when a session turns terminal (winner crowned, status `completed`, or `archived`). Specs in `review_minors_regression_spec.js`.

### 🟡 Port collision crashes with an unhandled error event, `voting-server/src/server.js:460`

**Problem**: `httpServer.listen(actualPort)` has no `error` listener. A second server on the same port dies with an unhandled `error` event and a stack trace (observed live during verification: `EADDRINUSE` killed the process after it had already connected to Mongo and recovered sessions).

**Why it matters**: The failure mode looks like a bug to the operator and happens after side effects (DB writes from recovery), instead of failing fast with one clear line.

**Suggested fix**: Attach an `error` handler on the http server (or use `listen` with a callback) and route the failure through the same fatal startup path `index.js` already has.

**Resolution (2026-09-21): Fixed.** The HTTP server attaches an `error` listener before `listen`; a busy port logs one clear line naming the port and exits with code 1 instead of an unhandled error stack. The spec stubs `process.exit` and asserts the handler ran.

### 🟡 Voter cookie lacks HttpOnly and Secure, `voting-server/src/server.js:263`

**Problem**: The `Set-Cookie` for the voter token sets only `Path` and `SameSite=Lax`. No `HttpOnly`, no `Secure`.

**Why it matters**: Any XSS in the client can lift the voter token from the cookie, though it can also read it from `sessionStorage` today, so HttpOnly alone does not close the hole. Worth fixing together with where the token lives, and `Secure` should accompany HTTPS deployments.

**Suggested fix**: Add `HttpOnly` and `Secure` when serving over HTTPS, and consider dropping either the cookie or the body copy so the token lives in one place.

**Resolution (2026-09-21): Fixed.** The join cookie now sets `HttpOnly` alongside `SameSite=Lax`, and adds `Secure` when the request arrived over HTTPS (direct TLS or an `x-forwarded-proto` proxy header). The client reads voter tokens from browser storage, never from the cookie, so nothing broke. The REST join spec asserts the flags.

### 🟡 Tournament math duplicated in the client reducer, `voting-client/src/redux/voteSlice.js` (handleVote, handleNext)

**Problem**: The client re implements tallying and round advancement (`handleVote`, `handleNext`) that mirrors `core.js` and the server reducer. The project rule says the server is authoritative and the client renders state and emits intent.

**Why it matters**: Two implementations of voting math drift silently. The local optimistic result is also wrong under ties (it counts a tie as both advancing locally) until the authoritative `session_state` overwrites it, so users can briefly see incorrect standings.

**Suggested fix**: Let `VOTE` and `NEXT` on the client be no op placeholders (or pure optimistic markers without math) and rely entirely on the server's `session_state` broadcast, which already arrives in the same tick over a local connection.

**Resolution (2026-09-21): Fixed.** Client `handleVote` and `handleNext` are documented no ops; tallies, pairs, and winners are written only by the server's `session_state` broadcast. New `server_authority_spec.js` pins that contract, and two `voting_spec.js` tests that asserted the old local math were rewritten to it.

## Nits

- ⚪ `voting-server/src/server.js:815`, the legacy `cookies['voter_token']` fallback name is dead weight now that tokens are session scoped; remove or log when hit.
- ⚪ `voting-server/src/server.js:488`, the sessions summary diff runs `JSON.stringify` on the full registry twice per store change; fine at this scale, but a version counter would be cheaper.
- ⚪ `voting-client/src/redux/voteSlice.js` (normalizeSession), the default status when none is present is `open`, which invents an active state from thin air; `pending` is the truthful default.
- ⚪ `voting-client/src/services/auth.js:38`, the JWT expiry check uses `atob` without base64 url handling; it silently falls back to trusting the token, which is fine only because the server revalidates anyway.
- ⚪ `voting-server/src/server.js:932`, monkey patching `io.close` to clear timers works but a wrapper or teardown function would be easier to discover.

## Strengths

- The `closeRoundOnce` design is the best part of the codebase: one idempotent gate, stale round guards on both timer paths, and a frozen `finalVote` snapshot. The invariants documented at the top of `roundManager.js` are real and testable.
- Both test suites are unusually thorough for a project this size: round lifecycle, reveal hardening, early completion, timer contracts, persistence recovery, plus client reducer and middleware specs.
- `LOCAL_ACTION_TYPES` echo loop prevention and the `normalizeSession` token stripping are exactly the right guards for a socket bridged store, and they are consistently enforced.
- Startup recovery is thoughtfully conservative: interrupted `open` sessions reset to `pending`, archived sessions stay out of the runtime registry, and the `isTournamentProgression` guard stops NEXT from corrupting the stored entry roster.

## Test coverage

TESTS = configured on both packages (node --test on the client, Mocha with mongodb-memory-server on the server), and coverage of the engine is genuinely good. What the suites miss maps to the findings above: nothing emits `SET_ROUND_LIFECYCLE` from an untrusted socket (would have caught the blocker), nothing drives admin `NEXT` inside the reveal window (would have caught the double advance), and the duplicate vote specs only ever vote once per pair, so the re-paired pair collision is invisible. The bcrypt login path has no test for concurrent or repeated attempts, which is where the missing throttle would show.

**Update (2026-09-21)**: the gaps named above are now covered by the regression specs written alongside the fixes: untrusted `SET_ROUND_LIFECYCLE` (`ingress_allowlist_spec.js`), admin NEXT inside the reveal window (`reveal_next_regression_spec.js`), the same pair meeting again plus login throttling (`review_majors_regression_spec.js`), memory cleanup and cookie flags (`review_minors_regression_spec.js`), and the client authority contract (`server_authority_spec.js`). The throttle was later hardened from identifier keying to IP keying with a shared unknown identifier pool (`ip_throttle_regression_spec.js`), closing the identifier rotation hole noted in the caveat above. Counts at resolution time: 368 server tests, 283 client tests, all passing; 378 server tests after the throttle hardening.

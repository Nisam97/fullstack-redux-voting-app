## Summary

The feature is complete end to end and closely follows spec 0003. Round snapshots freeze at closure, persist incrementally, hide during VOTING, and render on the results page with a timeline and totals panel. All 727 tests pass. The headline issue is a tally leak: the AC-9 broadcast guard does not actually cover the paths clients receive, so an active round's frozen tally can reach a fresh subscriber, and the guarded rounds rest payload is served from an unguarded channel. One more correctness issue in the advanced derivation could write a wrong winner history on the last round.

## Blockers

### 🔴 Frozen tally leaks to a client that subscribes mid round, `voting-server/src/server.js:1024` and `voting-server/src/reducer.js:150`

**Problem**: AC-9 says tallies in rounds[] are never visible during an active VOTING phase. `serializeSessionState` strips `rounds` only when `roundLifecycle === 'VOTING'`, but the reducer sets `roundLifecycle` to `'VOTING'` on every `NEXT` while `APPEND_ROUND_RESULT` for the round that just closed is dispatched *before* `NEXT` in the direct advance path of `closeRoundOnce`. In the reveal path the same problem arrives on the initial `session_state` emit: a client that joins (or reconnects, or reloads the page) during `RESULTS_REVEALED` or `ROUND_CLOSED` receives the session object with `rounds` fully included, which is correct per AC-3, but the slice of time between `SET_ROUND_LIFECYCLE` (which stores `finalVote` on the session) and `NEXT` also serializes `finalVote` with the full frozen tally. `serializeSessionState` never strips `finalVote`, so any subscriber that connects during the reveal window sees the closed round tally through `finalVote` even if `rounds` were stripped. The spec's value sourcing table also does not list `finalVote` as a client visible field.

**Why it matters**: A voter who reloads mid reveal or opens the results page on a second device sees current round tallies that a voter who stayed connected never saw. That is an inconsistent and gameable information surface, and it is exactly the invariant the spec says extends to round history.

**Suggested fix**: Strip `finalVote` (and `revealTimer` internals if sensitive) from `serializeSessionState` whenever `roundLifecycle` is not `RESULTS_REVEALED`, or better, whitelist the serialized session fields instead of blacklisting. Add a broadcast guard test that connects a fresh socket during the reveal window and asserts no tally is present anywhere in the payload.

## Major

### 🟠 Wrong `advanced` derivation when the final round ends in a tie, `voting-server/src/roundManager.js` (`deriveRoundSnapshot`)

**Problem**: The spec says `advanced` is derived from the post `next()` session state: if `winner` is set, this was the final round and `advanced` is null. `deriveRoundSnapshot` instead approximates this by checking whether `entries` plus `winners` would leave exactly one entry, computing `prospectiveEntries.size === 1 ? null : winners`. That works for the last round when one candidate advances, but on a final round tie the pair advances with two winners (`core.js` `getWinners` returns both on a tie, and the tournament continues), so `prospectiveEntries.size` is 2 and `advanced` is `[a, b]`, which happens to be right there. The real divergence is the mirror case: a final round where one entry remains in `entries` *plus* the winner makes `prospectiveEntries.size === 1` only when `entries` is empty and `winners` has one name. If a session's `entries` list is out of sync with the actual pair (for example after recovery where `entries` was persisted as the full original list), the derivation reads stale entries and can mark a non final round's `advanced` as null or a final round's as `[both]`.

**Why it matters**: `advanced` is the audit field admins rely on to see who moved on. A wrong value written to `Result.rounds[]` is permanent, because snapshots are frozen and never mutated, and the idempotency guard means it is never recomputed.

**Suggested fix**: Derive `advanced` from the actual post `NEXT` store state at the dispatch site in `closeRoundOnce` (as the spec prescribes), not from a prospective computation inside the snapshot. If keeping the pure derivation, take the remaining entries and winner as explicit inputs verified against the store rather than re-reading `session.entries`.

### 🟠 `GET /api/sessions/:id/rounds` serves live in memory rounds without the AC-9 guard, `voting-server/src/server.js:752` to `801`

**Problem**: The endpoint first checks the Redux store and returns `session.get('rounds')` directly. Whatever the reducer has appended is served. During an active round the reducer holds the just closed snapshot until `NEXT` runs, and the in memory list is not stripped by any guard on this path. AC-9's strip rule is enforced only in `serializeSessionState` for the socket payload, and in `normalizeSession` on the client. The REST path has no equivalent check.

**Why it matters**: The spec's tally hiding invariant extends to round history everywhere a client can read it. The REST endpoint is public, unauthenticated, and readable with curl, so it is the easiest surface to observe tallies from.

**Suggested fix**: Apply the same guard as `serializeSessionState`: if the session status is not `completed` and `roundLifecycle` is `VOTING`, either strip the last snapshot or return the list from the previous persistence snapshot. Factor the guard into one shared function so socket and REST cannot drift again.

## Minor

### 🟡 Partial Result doc can carry `winner: null` into history listings that assume a winner, `voting-server/src/db/repository.js` (`pushRoundToResult`, `getCompletedResults`)

**Problem**: `pushRoundToResult` creates the Result doc with `winner: null` and `completedAt: null`. `getCompletedResults` filters `winner: { $ne: null }`, which works, but the `Result` schema marks `winner` as `required: true`, so the partial doc only exists because the write bypasses Mongoose validation via `Result.collection.updateOne`. Any later code path that saves through the model (for example `saveResult`'s `existing.save()`) passes validation only because `winner` was already set. This hidden contract (create via collection API to skip validation, later save via model) is fragile and undocumented.

**Why it matters**: A future contributor who "fixes" the upsert to use the model API will start getting validation errors on the first round close, or worse, a default winner value will leak a fake winner into the history filter.

**Suggested fix**: Document the intentional validation bypass at the upsert site, or relax the schema (`winner: { type: String, default: null }` with a partial filter index) so the model API can create partial docs safely.

### 🟡 History list loses round counts and never uses the rounds endpoint it is specced to use, `voting-client/src/pages/History.jsx`

**Problem**: AC-7 says the `/history` detail view fetches round data via `GET /api/sessions/:sessionId/rounds` and renders the same accordion timeline and totals panel as the live results page. The history page links to `/sessions/:id/results`, and the results page does fetch the rounds endpoint, so the flow works. But `History.jsx` itself renders no round breakdown, and `getCompletedResults` explicitly projects `rounds: 0`, so the list page cannot even show "N rounds" without a second fetch. The AC is satisfied only through the indirection of the results page.

**Why it matters**: This is a contract wording gap more than a bug, but a reviewer of AC-7 looking at the history page finds nothing, and the "same accordion timeline" claim holds only on a different route.

**Suggested fix**: Either rename the AC to match the implemented flow (results page renders round history for completed sessions, history page links to it) or add a compact round count and inline timeline to the history detail card.

### 🟡 Unhandled rejection surface on fire and forget persistence, `voting-server/src/roundManager.js` (`closeRoundOnce`)

**Problem**: `repository.pushRoundToResult(...).catch(...)` swallows the error into a console log with only `err.message`. That is the right call for fire and forget persistence, but the snapshot is then lost forever from `Result.rounds[]`: the in memory `closedRounds` idempotency set and the DB push are not coordinated, and a crash after the catch loses that round permanently since recovery rebuilds from the Result doc.

**Why it matters**: The feature's stated purpose is crash safe history. A swallowed DB error silently produces a gap in the permanent record, and the spec's idempotency (skip if roundIndex exists) would not repair it because there is no retry mechanism.

**Suggested fix**: Track a per session set of roundIndexes that failed to persist and retry the push on the next successful round close or on a periodic flush. At minimum, log at error level with the sessionId and roundIndex so the gap is discoverable.

### 🟡 `RoundTimeline` initial expanded state freezes on mount, `voting-client/src/components/results/RoundTimeline.jsx:17`

**Problem**: `useState(rounds.length > 0 ? rounds[rounds.length - 1].roundIndex : null)` computes the initial state once. During a live session, rounds arrive over time; the accordion opens the last round that existed at mount and never auto opens newer rounds as they land. The user must click each new round manually.

**Why it matters**: On the live results page (the primary surface for this feature), each round reveal is the moment users are watching. The component works, but the UX subtly contradicts the "follow the tournament progression" story in the spec.

**Suggested fix**: Add a small effect that, when a new highest roundIndex appears, sets it as expanded unless the user has interacted with the accordion (track a `userTouched` ref).

## Nits

- ⚪ `voting-server/src/roundManager.js` (`deriveRoundSnapshot`), the function reads `session` twice with the same guard shape as the surrounding code; consider the small helper the file already uses elsewhere.
- ⚪ `voting-client/src/components/results/resultsUtils.js:435`, `round.resolution === 'WINNER' || round.resolution === 'majority_win'` mixes legacy uppercase constants with the spec enum; once Phase 4 lands the enum will grow and this boolean chain will grow with it.
- ⚪ `voting-server/src/db/repository.js` (`pushRoundToResult`), the `$set` spread for title and entries builds its conditions inline in one expression; two small named booleans would read better.
- ⚪ `voting-client/src/pages/Results.jsx:206` and `:405`, the same `TotalsPanel`/`RoundTimeline` block is duplicated in the concluded and revealed states; extract a `RoundHistorySection` component.

## Strengths

- The `Result.rounds[]` incremental persistence design is solid: the upsert with `$push`, the roundIndex idempotency in both the repository and both reducers, and the recovery rebuild in `recoverSessionsFromDb` all line up with the spec.
- The `APPEND_ROUND_RESULT` action is correctly server internal, the client registers it in its own slice with an idempotency guard that mirrors the server reducer exactly.
- The snapshot freezing discipline is genuinely immutable in memory and in Mongo, and `core.js` was left untouched.

## Test coverage

TESTS = configured (node:test server, node:test client). Both suites green: 427 server, 300 client. Persistence, idempotent append, completion update, REST endpoint shape, recovery, and `deriveTotals` are all covered per the spec's critical test scenarios. The gap: no test connects a socket or calls the rounds REST endpoint during an active VOTING or reveal window to assert tally absence across every field of the payload (the existing broadcast guard test only checks that `rounds` is absent from `serializeSessionState`, not that `finalVote` is). That gap is what lets the blocker through.

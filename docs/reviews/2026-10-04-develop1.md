## Summary

The change builds the results visibility matrix the spec asked for: a shared `resolveResultVisibility` gate over the result, rounds and lobby reads, a repository level history filter, an admin only `SET_PUBLISH_RESULTS` action, an admin only turnout view over the existing `VoteParticipation` trail, and a client that renders a neutral gated state. The server side is careful and the test suite is unusually thorough: 14 sections map every acceptance criterion to an integration test, and the leak guards scan real payloads rather than asserting on helpers. Both suites pass (server 681, client 442 unit plus 52 component). The one problem that should block merge is on the client: the publish toggle tells the admin the value it wanted to set, not the value the server accepted, and nothing on that page hears the server's refusal.

## Major

### 🟠 The publish toggle reports the requested state, and nothing on the Results page hears the server refuse it, `voting-client/src/pages/Results.jsx:141`

**Problem**: `handleTogglePublish` (line 141) writes the new value into `historicalResult` and dispatches `SET_PUBLISH_RESULTS`, which the slice also applies to `bySessionId` (line 886). Both flips happen before the server answers. The remote action middleware (`voting-client/src/redux/store.js:147`) only enriches, emits, and calls `next(action)`; it has no success and no failure path. When the server refuses, `respond` (`voting-server/src/server.js:2707`) emits `action_error`, and the only listeners in the client are `voting-client/src/pages/Admin.jsx:143` and `voting-client/src/pages/Voting.jsx:174`, neither of which is mounted on the Results route. So a rejection produces no message and no rollback, and the optimistic flip stands until the page reloads.

**Why it matters**: the refusal paths are real, not theoretical. The admin JWT carries a 24h expiry and `isAdminLoggedIn` only re checks it on render, so a click after the token lapses returns `UNAUTHORIZED`. `SESSION_NOT_COMPLETED` fires if the client's copy of the status has drifted, and `DATABASE_ERROR` fires when the `Session` or `Result` write fails. In the unpublish direction the admin is shown "Private: only approved participants and you can view this result" while the result is still world readable on `/history`, `/result` and `/rounds`. That is precisely the misreading this feature exists to prevent. The server stays authoritative and correct, so the bug does not expose anything by itself, but it removes the operator's ability to know whether a secured result is exposed.

**Suggested fix**: make the server's answer the source of truth. Either emit with an ack callback and apply the flip only on `success`, or have the Results page listen for `action_error` carrying `SET_PUBLISH_RESULTS` and revert both `historicalResult` and the store copy, showing a short error line beside the button. Add a component test that a rejected publish leaves the toggle reading "Private result" and that the failure is visible to the admin.

## Minor

### 🟡 The public history filter widened to every completed row, untested and not in the spec, `voting-server/src/db/repository.js:382`

**Problem**: `getCompletedResults` changed from `winner: { $ne: null }` to `completedAt: { $ne: null }` plus the type filter. A session terminated with `no_result` (`voting-server/src/roundManager.js:1335` writes `winner: null` with a fresh `completedAt`) was excluded from the archive before and is listed now. `voting-client/src/pages/History.jsx:124` renders `{item.winner}` inside a winner banner, so such a row shows an empty banner. No test pins either direction: `grep 'winner: null' voting-server/test/*.js` returns nothing.

**Why it matters**: AC-1 says a public session's completed result is visible "exactly as today" and AC-13 says public visibility is unchanged. The repository comment calls the widening intentional, but it is neither in the spec nor asserted anywhere, so it can be reverted or tightened later without anything failing.

**Suggested fix**: decide which behavior is wanted. Restore the winner filter if the change was incidental to the type filter, or keep it, say so in AC-1, and add one test asserting a completed no winner session is listed. Give the history row a neutral label when `winner` is null either way.

### 🟡 Securedness is read from `type` alone, and every derivation fails open, `voting-server/src/server.js:766`

**Problem**: three places decide whether a session is secured, all from a `type` field with a public default: `resolveSessionAccess` (`server.js:766`) returns `isSecured: false` when neither the store nor the database can produce the session, the lobby uses `session.get('type') || session.get('sessionType') || 'open'` (`server.js:1709`), and the result and rounds gates pass `access.isSecured` as the fallback that `resolveResultVisibility` only consults when the `Result` row carries no `type` itself. `whoCanJoin !== 'public'` sits on both the store session and the `Session` document and is never consulted on these paths.

**Why it matters**: the combination that matters is a legacy `Result` row with no `type` (created before the backfill) plus a session lookup that fails or finds nothing: the gate then resolves to `public` and serves the result to everyone. The spec's Risks section accepts the orphan case, but it assumes the backfill has run. `backfillResultTypes` failures in `voting-server/index.js:41` are caught and only logged, so a failed backfill leaves exactly that state while the server starts up looking healthy. A privacy gate defaulting to open is the wrong direction for an unexpected state.

**Suggested fix**: fail closed when a result's type cannot be resolved and the session behind it cannot be found either, or at minimum make the backfill failure loud (non silent warn with a count of rows it could not process) and consider `whoCanJoin` as a second signal in the lobby and result gates. If the open default is deliberate, note it in the Risks section as a failure of the backfill, not only as an orphan row.

### 🟡 `setPublishResultsPublicly` writes two documents in sequence, not the single step AC-3 requires, `voting-server/src/db/repository.js:406`

**Problem**: the helper runs `Session.updateOne` and then `Result.updateOne` with no transaction and no compensation between them, while AC-3 requires the flag to be written to both rows "in one step so they never drift".

**Why it matters**: if the second write fails, `Session.publishResultsPublicly` is flipped and the `Result` is not. The store dispatch is skipped on error, so reads stay consistent in the meantime (the resolver and history both read the `Result` row, and the lobby gate reads the store). The drift surfaces later: after a restart, `recoverSessionsFromDb` hydrates the flipped `Session` row into the store, the lobby gate opens and serves the secured `winner` to anonymous callers while `/history` and `/result` still hide the result. Low probability, and safe until a restart, but the two rows do drift, which is the one thing the AC says cannot happen.

**Suggested fix**: use a transaction where the deployment has a replica set, or write the `Session` row first and roll it back if the `Result` write throws, or treat the `Result` row as the only published source for reads (it already is) and stop mirroring the flag onto `Session`. Whatever the choice, make the comment match the code.

## Nits

- ⚪ `voting-client/src/pages/Results.jsx:146`, `publishBusy` clears on a hardcoded 400 ms timer rather than on the server's answer, so a slow rejection still reads as a successful toggle for that window.
- ⚪ `voting-server/src/server.js:1726`, AC-2 says the lobby "omits the `winner` field" for a gated session; the code sets `winner = null`, so the key is still present. Every current consumer handles null, this is just not literally what the criterion says.
- ⚪ `voting-client/src/redux/voteSlice.js:1638`, `selectTurnout` returns a fresh `[]` when there is no turnout, which trips react-redux's stability warning on `Results.jsx:64` during the component tests. It copies the existing `selectSessionRounds` pattern, so it matches the codebase rather than regressing it.
- ⚪ `voting-server/src/server.js:1689`, the lobby answers `200` with title, status, `whoCanJoin`, `entryCount` and `voterCount` for a gated secured session while an unknown id answers `404`, so existence is still distinguishable by anyone holding a session id. The spec's API table deliberately keeps the lobby public and gates only `winner`, so this reads as intended, but AC-2's closing sentence "The existence of the session is not revealed" sits right next to the lobby carve out and is ambiguous enough to deserve one clarifying line in the spec.

## Strengths

- One shared `resolveResultVisibility` feeds the result, rounds and lobby gates, and the history filter is expressed as the same predicate in the repository, which is exactly the spec's Decision and is what keeps the surfaces from drifting apart. Denial is `404` with the missing result body everywhere, and the participant lookup fails closed (`catch` returns `false`).
- `voting-server/test/visibility_and_privacy_spec.js` runs to 1023 lines and 14 sections that map every acceptance criterion to an integration test. The leak guards scan real payloads: the registry, `session_state`, the secured lobby, an anonymous `NOT_ELIGIBLE` refusal, a genuinely joined member's payload, and a gated 404 body.
- `emitSessionTurnout` checks the room and skips its database reads entirely when no admin holds it, so the new per round query costs nothing on the hot path.

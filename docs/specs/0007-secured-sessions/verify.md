## Environment notes for whoever runs this next

- The shell exports `PORT=0`. `index.js` reads `process.env.PORT`, so `npm start` binds port 0 instead of 8090. Launch with `PORT=8090 node -r @babel/register index.js`.
- The real admin socket protocol: actions go out on `action`. Handled responses arrive through the Socket.io ack callback. Early validation failures emit `action_error` and never ack. `CREATE_SESSION`, `START_SESSION` and `NEXT` never ack; read the authoritative result from the `sessions` broadcast instead.
- The `sessions` broadcast payload is a bare array of session summaries, not an object with a `sessions` key.
- `CREATE_SESSION` needs `sessionId`, `title` (non blank) and `entries` (2 or more distinct plain strings). The session type field is `sessionType`, because `type` is the action type itself. Join codes are generated by the server; read the generated code off the broadcast, a supplied `joinCode` is ignored.
- `VOTE` takes `entry` (a candidate name from the active pair). A successful `VOTE` never acks. In a tournament the active pair advances the moment a vote lands, so a second vote for the same round needs a second voter holding the pair open.
- `subscribe_session` takes no ack callback. Passing one hangs the caller forever.
- Join codes are 6 characters and the resolver requires exactly 6 alphanumerics after uppercasing and stripping everything else.

### Defect found during the first run, now fixed

**The admin client socket never carried the admin token, so secured sessions were invisible in the admin panel until you manually reconnected.**

`voting-client/src/services/socket.js` created the singleton with no handshake `auth`, and `voting-client/src/services/auth.js` set `socket.auth` only after a successful login, which Socket.io does not resend once the socket is connected. `isSocketAdmin` therefore returned false and `broadcastSessions` filtered every secured session out of the admin list.

Fixed after that run: `socket.js` reads the stored JWT at construction and passes it as handshake `auth`, and a new `applyAdminTokenToSocket(token)` sets the token and reconnects whenever it changes; `loginAdmin` and `logoutAdmin` both call it. Confirmed in that run's browser session with no manual intervention. Regression coverage lives in `voting-client/test/admin_socket_auth_spec.js`.

### AC-13, restart resilience: now fully exercised

Three phases around a real process restart, not a simulated one.

1. Voter `restart.1791173550599@example.com` signed in over the OTP flow, was allowlisted, joined secured session `vsx_restart_1791173550599`, admin started it, voter voted for `Alpha`. One `VoteParticipation` doc written, `roundId` `vsx_restart_1791173550599:::r1`.

Rejoining with the **same** cookie returned 200 and `voterToken` `user:6ac323af04bec3cc7fcbb486`, identical to before the restart, so the identity is cookie derived and survives. The pre restart doc was still there, count 1, same round id.
3. A direct re-vote in that state returned `SESSION_NOT_OPEN`, not `DUPLICATE_VOTE`, because recovery deliberately re-registers every session as `pending` rather than resuming a live tournament (`persistence.js:380` explains the choice). So the admin restarted the session, the same voter voted for the same pair again, and the server answered `DUPLICATE_VOTE`, with the doc count still 1. That is the AC-13 guarantee: a round id that repeats across a restart still carries the pre restart participation record, and the compound index plus the record refuse the second ballot.

Worth knowing for the next reader: the `DUPLICATE_VOTE` half of AC-13 cannot be reached until the admin restarts the recovered session, because recovery never resumes a live one. The earlier runs' `DUPLICATE_VOTE` claim after a restart depended on the same step.
